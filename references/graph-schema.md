## Purpose and lifecycle

A development graph is a persistent JSON state machine for Complex development work. It determines which node can run, which edge is selected by an outcome, how many times a loop may be traversed, and whether completion is valid. It does not execute the work inside a node.

Create the definition with the Plan. Before approval, validate it and generate the same-name SVG preview. After approval, initialize it:

```powershell
python <absolute-skill-path>\scripts\dev_graph.py validate <graph.json>
python <absolute-skill-path>\scripts\dev_graph.py render <graph.json>
python <absolute-skill-path>\scripts\dev_graph.py init <graph.json>
```

`init` deliberately resets runtime state. Use it initially or after an approved topology/pass-condition change, never to erase an inconvenient failure. Reinitializing a graph with existing history requires `--approval-evidence "<user approval>"`; the executor stores that evidence in the new runtime.

Early Schema v1 runtimes created before `initialization_evidence` existed remain readable as an empty value so their append-only history is not erased. Every newly initialized runtime writes the field explicitly.

## Runtime selection

Runtime probing is only for Complex work. Select one executor for the task:

| Priority | Runtime | Script | Requirement |
| --- | --- | --- | --- |
| 1 | Python | `scripts/dev_graph.py` | Actually runnable Python 3.10+; reject broken aliases. |
| 2 | Node.js | `scripts/dev_graph.mjs` | Node.js 18+ using only built-in modules. |
| Stop | None | — | Record the blocker; do not downgrade to a prose-only graph. |

Python and Node.js use the same Schema v1 definition, canonical SHA-256, history chain, status snapshots, edge counters, commands, and exit codes. A graph initialized or advanced by either executor can be continued by the other.

## Graph fields

| Field | Type | Meaning |
| --- | --- | --- |
| `schema_version` | integer | Must be `1`. |
| `id` | string | Stable graph identifier. |
| `title` | string | Human-readable task title. |
| `spec` | string | Path to the approved Spec. |
| `plan` | string | Path to the approved Plan. |
| `entry` | string | Initial non-terminal node ID. |
| `required_gates` | string array | Gates every successful path must traverse. |
| `nodes` | node array | Immutable node definitions. |
| `edges` | edge array | Conditional transitions. |
| `runtime` | object | Generated by `init`; do not author manually. |

Spec, Plan, and graph paths are resolved relative to the artifact containing the link. Keep all three mutually linked.

## Node fields

Every node has:

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | string | Unique semantic identifier. |
| `title` | string | Semantic title, not `step-1`. |
| `type` | enum | `action`, `gate`, `approval`, `decision`, or `terminal`. |
| `owner` | string | `main-agent`, `user`, or another explicit owner. |
| `inputs` | string array | Approved artifacts or evidence required by the node. |
| `outputs` | string array | Artifacts or evidence produced by the node. |
| `pass_condition` | string | Objective condition for a `pass`. |
| `required` | boolean | Whether the node must be reachable from the entry. |
| `handler_skill` | string, optional | Skill used inside the node. |

A terminal additionally has `outcome: "success"` or `outcome: "stopped"`. Terminal nodes have no outgoing edges. Gates must have a `fail` edge. IDs referenced by `required_gates` must be gate nodes.

## Edge fields

Every edge has `from`, `to`, and `event`.

Valid events:

- `pass`: the node met its pass condition;
- `fail`: the node produced failure evidence;
- `blocked`: an external blocker prevents progress;
- `scope_change`: the approved topology or pass condition must change.

Use `max_traversals` with a positive integer on every edge that closes a loop. Removing all bounded edges must leave a DAG. This makes every retry path finite.

Each non-terminal node should normally define all four events. A missing selected event is a transition error, not permission to improvise.

## Runtime state and invariants

`init` creates:

```json
{
  "definition_hash": "sha256 of immutable definition",
  "statuses": {"node-id": "pending-or-ready"},
  "edge_traversals": {},
  "history": []
}
```

Valid statuses are `pending`, `ready`, `running`, `passed`, `failed`, `blocked`, and `skipped`.

The executor enforces:

- only `ready` may become `running`;
- only `running` may emit an outcome;
- every outcome has non-empty evidence;
- a selected bounded edge cannot exceed `max_traversals`;
- alternative immediate branch targets become `blocked`;
- a selected target becomes `ready`, including a previously failed retry target;
- history is append-only and SHA-256 chained;
- runtime snapshots must match the history chain;
- topology changes invalidate `definition_hash` and require approved reinitialization;
- completion requires a passed success terminal and evidence-bearing passes for all `required_gates`.

## CLI commands

Resolve the selected script relative to the loaded Skill and use its absolute path. The command shape is identical for Python and Node.js:

```powershell
python <tool> init <graph.json>
python <tool> init <graph.json> --approval-evidence "user approved revised Spec, Plan, and graph"
python <tool> validate <graph.json>
python <tool> ready <graph.json>
python <tool> start <graph.json> <node-id>
python <tool> pass <graph.json> <node-id> --evidence "command and result" --output "artifact"
python <tool> fail <graph.json> <node-id> --evidence "failure output"
python <tool> block <graph.json> <node-id> --evidence "external blocker"
python <tool> scope-change <graph.json> <node-id> --evidence "changed requirement"
python <tool> status <graph.json>
python <tool> render <graph.json> [--output <preview.svg>]
```

Node.js equivalents use the same arguments:

```powershell
node <tool> init <graph.json>
node <tool> init <graph.json> --approval-evidence "user approved revised Spec, Plan, and graph"
node <tool> validate <graph.json>
node <tool> ready <graph.json>
node <tool> start <graph.json> <node-id>
node <tool> pass <graph.json> <node-id> --evidence "command and result" --output "artifact"
node <tool> fail <graph.json> <node-id> --evidence "failure output"
node <tool> block <graph.json> <node-id> --evidence "external blocker"
node <tool> scope-change <graph.json> <node-id> --evidence "changed requirement"
node <tool> status <graph.json>
node <tool> render <graph.json> [--output <preview.svg>]
```

Never combine `start` and its outcome into one uninspected shell chain. Run the node's real work between the two commands and inspect its output before recording evidence.

### SVG preview

`dev_graph.py render` and `dev_graph.mjs render` create a deterministic, dependency-free SVG. Without `--output`, `path/name.json` produces `path/name.svg`. The preview shows every node and edge, event labels, bounded traversal counts, terminal outcomes, and current runtime status colors. It contains no scripts or external resources and safely escapes graph text.

Always run `validate -> render` after authoring or changing a graph definition. The mutating `init`, `start`, `pass`, `fail`, `block`, and `scope-change` CLI commands refresh the default SVG automatically. A preview is derived and replaceable; never edit it as runtime state or use it instead of the JSON execution ledger.

## Common failures

| Failure | Required response |
| --- | --- |
| Definition hash changed | Record scope change, obtain approval, then `init`. |
| Node is not `ready` | Run `ready`; do not bypass its predecessors. |
| Node is not `running` | Run `start` before recording an outcome. |
| Evidence is empty | Run and inspect the real gate; provide its fresh result. |
| Retry limit reached | Follow a stopped/approval route; do not increase the limit without approval. |
| History/runtime mismatch | Preserve the file, report tampering/corruption, and recover from an approved artifact plus evidence. |
| Required gate can be bypassed | Correct topology before implementation. |
